# Foundation identity and authentication contract (VP-003)

Canonical owner UUID is `auth.users.id`, mirrored by `profiles.id`; UUIDs are opaque to clients. Receipt guests are never canonical users. Profiles are created by a least-privilege security-definer trigger and existing Auth users backfilled. Auth metadata is bounded and copied once; no profile editing endpoint is introduced. Repeated/concurrent trigger invocations do nothing on existing UUID. Browser roles have only own-profile SELECT; writes and anonymous reads are denied. Auth user deletion cascades.

`GET /api/v1/me` requires exactly one `Authorization: Bearer <Supabase access JWT>`. No query parameters or X-User-ID are accepted. Response `200 {"profile":{"id":"UUID","display_name":"...","email":"...","avatar_url":"...","created_at":"ISO8601","updated_at":"ISO8601"}}`. Browser text is rendered escaped; avatar URL is never rendered/fetched. Only the caller's profile is returned; no provider/session credentials. Error follows DESIGN §27: `{"error":{"code":"...","message":"...","request_id":"..."}}`. Statuses: 400 invalid input; 401 authentication rejected; 403 disallowed origin; 405 unsupported method; 429 bounded validation capacity; 503 auth/profile unavailable. All profile/auth errors and successes use `Cache-Control: no-store`; no per-user response cache.

Backend configuration: SUPABASE_URL, SUPABASE_ANON_KEY (public key), WEB_ORIGIN; API_PORT defaults 8080. HTTPS required except loopback local HTTP. No service-role key or Google credential is needed by the API. Unverified JWT parsing is only a rejection prefilter (bounded header, UUID, expiry/not-before, exact issuer/audience). Every accepted token must then be cryptographically verified by Supabase Auth `/auth/v1/user`; its nonanonymous returned UUID must equal JWT subject. An unverified token never enters request context. This deliberately uses provider verification for both symmetric and asymmetric signing keys; no backend signing secret or custom key rotation. Upstream origin is fixed operator configuration; redirects refused. Each request has 3s total budget, individual calls 2s, 64KiB response limit, max 16 active validation/profile requests, and no automatic retry. Malformed tokens hit no provider. Saturation returns 429 + Retry-After 1. No shared auth cache, key fetch, or negative token cache; availability depends on Auth. Later route owners call `foundation.API.Protect(handler)` and retrieve identity using `foundation.UserID(ctx)` only. Middleware must precede handlers. Profile DB access uses the verified caller token, preserving RLS even after API verification.

Browser uses Supabase PKCE, explicit code exchange, automatic refresh, SDK-managed local storage, and bearer-only API requests with credentials omitted. No auth cookies or cookie-based API authorization; CSRF via ambient cookies is therefore inapplicable. CORS permits exactly WEB_ORIGIN, GET and Authorization; no credentialed CORS or wildcard. PKCE verifier binds exchange to initiating browser. App callback URL is fixed same origin `/auth/callback`, destination always `/`; no user-selected redirect. Errors do not echo provider callback params, codes, tokens or internal messages. Callback URL cleared after success/failure. Sign-out uses SDK local scope to clear current-browser session/refresh state; an already-issued JWT can remain usable until expiry, as Supabase access JWT behavior dictates. HTTPS and XSS prevention remain necessary because SDK storage is readable by browser JS. Browser never authorizes itself from stored session/profile: Go verifies every API request. SDK requests have 10s bounds; profile fetch 5s. Buttons disable/deduplicate in-flight operations, loading/errors are accessible status/alert messages.

Official provider references: https://supabase.com/docs/reference/javascript/auth-getuser ; https://supabase.com/docs/guides/auth/sessions/pkce-flow ; https://supabase.com/docs/reference/javascript/auth-signinwithoauth . Shared-resource and security details require independent Integration Review.

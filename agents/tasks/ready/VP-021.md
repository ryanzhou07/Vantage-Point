# VP-021 — Participant payment method (Venmo / Zelle) on receivables

## Status
`READY`

## Owner
Receipt Agent (Integration/Review separate)

## Purpose
Venmo exposes no API for reading a user's activity, so Vantage-Point cannot detect Venmo repayments. Those stay manual: the owner marks them paid. Zelle repayments can later be matched from a connected bank account (VP-022). To support both, each participant says how they will pay, the owner sees that on the receivable, and the UI is honest about which rows can only be settled by hand.

## Scope
- Participants choose `VENMO` or `ZELLE` in the split session (the guest flow from VP-015) before they submit. They may change it until their submission is locked.
- Persist the choice on the participant and snapshot it onto the receivable at finalization (alongside amounts, which are already immutable).
- Return `payment_method` from the receivables list.
- Owner UI: show the method on each receivable. Venmo rows: existing manual "Mark paid". Zelle rows: show "Automatic matching needs a connected bank" until VP-022 lands, and keep the manual button as a fallback so no row is stuck.
- Participant UI: a two-option choice in the join/claims panel.

## Out of Scope
- Collecting or storing Venmo usernames, Zelle emails/phones or any payee handle (sensitive PII; needs a separate owner decision).
- Reading Venmo data, deep-linking into Venmo/Zelle, or moving money.
- Zelle auto-matching and bank access (VP-022, VP-018).
- Search/filter (VP-023–VP-025).

## Dependencies
VP-019 merged; VP-015a/b/c (session, QR join, claims). VP-020 recommended first but not required.

## Requirements
1. `payment_method` is one of `VENMO`, `ZELLE`, or unset. Unset is treated as manual-only and shown as "Not chosen".
2. The participant sets it only through the existing session bearer token for their own participant; no one can set another participant's method.
3. The owner cannot be forced into a method: the owner's own participant produces no receivable.
4. At finalization the value is copied to `receivables.payment_method` and never changes afterward.
5. Enum enforced in the database, not only in Go/TS.
6. Input validated and bounded; unknown values return 400.
7. Public session endpoints expose no other participants' payment methods.

## Acceptance Criteria
- [ ] A guest picks Venmo or Zelle in the session and it survives refresh.
- [ ] Finalizing copies each participant's method to its receivable.
- [ ] Owner sees "Venmo", "Zelle" or "Not chosen" on every receivable row.
- [ ] Setting an invalid method (`PAYPAL`, empty string, wrong type) is rejected by the API and by a DB check.
- [ ] A participant cannot set another participant's method (test).
- [ ] After finalization the method cannot be edited.
- [ ] Zelle rows explain that automatic matching is not available yet and still allow manual marking.

## Testing Requirements
- SQL assertions in `supabase/tests/` for the enum check and the finalize snapshot.
- Go: session-token authorization, invalid values, lock after submission/finalization.
- Component tests for the picker and the badge states.
- Targeted runs only.

## Shared Resource Impact
Shared contracts: YES (receipt session API, receivables list). Other domains: NO (Banking is untouched).

## Database Impact
`NEW MIGRATION` (Receipt domain): `payment_method` column with check constraint on `receipt_participants` and `receivables`; `create or replace` for `receipt_finalize` and `receivables_list`. Do not edit the applied `20261029000400` migration.

## Contract Impact
`NON-BREAKING CHANGE`: update `agents/contracts/RECEIPT_SESSIONS.md` (participant payload gains optional `payment_method`) and the receivables response (gains `payment_method`).

## Security Considerations
Payment method is not a secret but is participant data: keep it owner-only on receivable reads and off public session views. Do not log it with names. Collecting handles is deliberately excluded.

## Financial Correctness Considerations
Amounts are unaffected. The method is metadata snapshotted with the amounts so a later participant edit can never change a finalized record.

# VP-015c — Open join and participant item claims (one person per item)

## Status
`READY`

## Owner
Receipt Agent (Integration/Review separate)

## Purpose
Anyone with the QR/link joins by typing their own name, sees the receipt items, and claims their own items. The owner no longer assigns every item.

## Scope
- Join with a typed name: backend creates a receipt-scoped participant (max `MaxParticipants`, name bounded, no canonical user). Picking an existing owner-added name stays supported.
- Join response includes items (id, name, amount_minor) and each item's current claimer.
- Claim/unclaim endpoint authorized by the share token plus the participant id returned at join. First version: one person per whole item line.
- Participant UI on `/split`: item list, tap to claim, tap own claim to release, per-person total preview from the backend.
- Owner screen shows claims live (existing realtime broadcast + refetch) and may still override.

## Out of Scope
Shared items, percentages, quantity splits, participant submit/reconfirm, finalization, receivables, accounts for participants, LAN/phone dev tooling.

## Dependencies
VP-015a, VP-015b merged.

## Requirements
1. Claim only while the session is ACTIVE and unexpired (`CheckSession`); expiry stops claims, data is untouched.
2. A claim on an item held by someone else returns a conflict (409); no silent steal. Concurrent claims resolve in the database (single atomic function or unique constraint on the item's allocation), never in Go or the browser.
3. A participant can only claim/release as their own participant id; ids are validated against the receipt.
4. Reuse the existing `allocations` table and exact integer preview (`Calculate`); no new money logic.
5. Tokens never logged/stored; join and claim rate limited per IP and per session.
6. Claims lock the receipt items: owner price/item edits after the first claim must not silently change claimed lines (reject with a clear error, per PROJECT.md "should not silently change items underneath claims").

## Acceptance Criteria
- [ ] A new device joins by typing a name and sees the items.
- [ ] Two participants racing for one item: exactly one wins, the other sees a conflict and the current holder.
- [ ] Owner sees claims update without a manual reload (or within the poll interval).
- [ ] Expired session rejects claims.
- [ ] Per-person totals sum exactly to the receipt total.

## Testing Requirements
Go: claim/conflict/expiry/foreign-participant/rate-limit. SQL: concurrent claim assertion. Web component tests for join-by-name and claim conflict. Targeted checks only (AGENTS.md §31).

## Shared Resource Impact
None outside Receipt. Possible Receipt-owned migration (claim function).

## Database Impact
Receipt-owned forward migration only; no reset.

## Contract Impact
Extends `agents/contracts/RECEIPT_SESSIONS.md` (join response, new claim route).

## Security Considerations
Token is the only credential; participant id is not a secret, so claims must also bind to the session. Cap participants per session to stop name spam.

## Production Note
The share link is built from `window.location.origin`, so in production it is the deployed web domain automatically. Production needs HTTPS, `WEB_ORIGIN` on the API set to that exact origin (CORS for the public join route), and `NEXT_PUBLIC_API_URL` pointing at the deployed API.

# VP-028 — Keep card and payment details out of anything other people can see

## Status
`READY`

## Owner
Receipt Agent (Integration/Review separate)

## Purpose
Receipt photos often show card details: card number or last four, card brand, authorization codes, cardholder name, a signature. Today the original image sits in a private bucket readable only by its owner, and no participant or session endpoint returns image bytes or paths, so other people never see it. Owner decision: remove confidential card information from the receipt data and images whenever they will be shown to other people; if they stay private to the owner, keeping them is fine. This task makes that a tested guarantee instead of an accident, so later features (30-day links, personal views, location) cannot leak it.

## Scope
1. **Owner-only originals (keep, but prove it).** Original images stay private to the owner. Add tests that no participant, session, share-link or receivables endpoint can return image bytes, an image path or a signed URL.
2. **Do not extract payment details.** The vision provider schema and prompt must exclude card numbers, last four digits, card brand, authorization or approval codes, cardholder name and signature. Instruct the model to ignore them.
3. **Server-side sanitizer on extracted text.** Before any extracted or owner-typed text (merchant, item names, location from VP-024, participant names) is stored for display or returned on a participant-visible path, run it through a sanitizer that:
   - removes or masks digit runs of 13–19 digits that pass a Luhn check (with or without spaces or hyphens),
   - masks patterns such as `****1234`, `XXXX 1234`, `ending in 1234`, `card #…`, `auth …`, `approval …`,
   - leaves ordinary item text, prices and quantities untouched.
4. **Never show the original image to other people.** If a future feature wants participants to see the receipt photo (to verify items), it must show a redacted derivative, not the original. Nothing of that kind is built here. Record the rule in the contract so a later task cannot skip it.
5. **No logging of extracted text or images.** Confirm logs and error messages never contain receipt text, card patterns or image data.

## Out of Scope
Pixel-level image redaction or OCR-based blurring (only needed if a participant-facing photo is ever added), deleting or expiring originals, bank or payment-handle storage (payee handles are not collected).

## Dependencies
VP-019 merged. VP-024 (location) and VP-026 (30-day links) must apply the sanitizer and the owner-only rule; add checks for them when they land.

## Requirements
1. The sanitizer is a single shared function with a table-driven test list, called at every write path for displayed text and at every participant-facing read path as defense in depth.
2. A string the sanitizer changes is not an error; it is stored masked and the owner sees the masked value in review.
3. Luhn-valid 13–19 digit runs are always removed even when spaced or hyphenated; order numbers, phone numbers and normal prices must not be mangled (negative tests).
4. Participant-visible responses are built from allowlisted fields, so a new database column is not exposed by default.

## Acceptance Criteria
- [ ] A fake extraction containing `VISA ****4242`, `4242 4242 4242 4242` and `Auth 839201` yields stored fields with those removed or masked.
- [ ] `Order #12345678`, `$1,234.56`, a 10-digit phone number and a 12-digit non-Luhn code remain untouched.
- [ ] A test enumerates participant, session, share-link and receivables responses and asserts none contains `image_path`, image bytes or a signed URL.
- [ ] The provider schema has no payment-detail fields (test on the schema).
- [ ] A grep or test confirms no log call prints extracted text.

## Testing Requirements
Unit: sanitizer table tests with positive and negative cases. Go API tests for the allowlisted response shapes. Authorization test that the image route accepts only the verified owner. Targeted runs only.

## Shared Resource Impact
Shared contracts: YES, add the participant-visible-data rule to `agents/contracts/RECEIPT_SESSIONS.md` and the extractor contract.

## Database Impact
`NONE` expected. Sanitizing happens in Go before storage. Add a DB check only if the Receipt agent finds a cheap, safe one.

## Contract Impact
`NON-BREAKING CHANGE` (documented rule plus allowlisted responses).

## Security Considerations
Limits of this approach, to state honestly in the implementation notes: the whole image, including card digits, is sent to the vision provider during extraction, and sanitizing the extracted text does not change that. Reliable automatic redaction of the photo before upload is not realistic. Keeping the original owner-only, never sharing it, and never storing card data in text fields is the achievable guarantee.

## Financial Correctness Considerations
Masking must never alter prices, quantities or totals. Run the sanitizer on text fields only, not on money fields.

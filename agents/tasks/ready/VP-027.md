# VP-027 — Lower receipt scan limits to cap model cost

## Status
`READY`

## Owner
Receipt Agent (Integration/Review separate)

## Purpose
Each receipt scan and each retry is a paid vision-model call. Today an owner may create 20 receipts per day (deletions count toward it), hold 5 in `DRAFT`/`PROCESSING`, and retry each failed extraction up to 2 times. Worst case is about 60 model calls per owner per day. The owner wants the allowance "very low" to keep cost small and abuse bounded.

## Scope
- Lower the limits and make them named, documented constants rather than numbers buried in SQL:
  - Uploads per rolling 24 hours: 20 → **5**.
  - Uploads per rolling 30 days: new cap of **20**.
  - Concurrent `DRAFT`/`PROCESSING` receipts: 5 → **2**.
  - Extraction retries per receipt: 2 → **1**.
- Friendly quota errors in the UI that say which limit was hit and when it resets.
- Show the owner their remaining scans (for example "3 of 5 scans left today").
- Deletion keeps counting toward the quota (existing behavior).

## Out of Scope
Paid plans or billing, per-user overrides, changing the model, manual receipt entry without a scan (allowed and free; confirm it still works under the quota), caching extraction results.

## Dependencies
VP-019 merged. None otherwise.

## Requirements
1. Limits live in one place in the Receipt schema (a new migration replacing the creation and retry RPCs) with the values above; the Go layer and UI read the same numbers from the API, not hard-coded copies.
2. Limits are enforced in the database transaction, so concurrent requests cannot exceed them.
3. A failed extraction that never reached the model (validation failures before the provider call) does not consume a retry.
4. The owner's own existing receipts and history are unaffected.
5. Error codes stay `RECEIPT_QUOTA` and `RECEIPT_RETRY_LIMIT`; the response gains the limit that was hit and `resets_at`.

## Acceptance Criteria
- [ ] The sixth upload within 24 hours is rejected with `RECEIPT_QUOTA` and a reset time.
- [ ] The 21st within 30 days is rejected even if the daily limit has room.
- [ ] A third concurrent draft is rejected.
- [ ] A second retry on the same receipt is rejected with `RECEIPT_RETRY_LIMIT`.
- [ ] Ten simultaneous upload requests produce at most the allowed number of accepted receipts (concurrency test).
- [ ] The UI shows remaining scans and a clear message at the limit; manual entry still works.

## Testing Requirements
SQL assertions for each limit and the rolling windows; Go tests for error shape; concurrency test; component tests for the remaining-scans text and the limit messages. Targeted runs only.

## Shared Resource Impact
Shared database: NO. Shared contracts: YES (`RECEIPT_QUOTA` payload gains fields).

## Database Impact
`NEW MIGRATION` (Receipt): replace the receipt-creation and retry RPCs. Do not edit applied migrations.

## Contract Impact
`NON-BREAKING CHANGE`: additive fields on the quota error and a remaining-scans field on a read endpoint.

## Security Considerations
Limits are per verified owner, never per client-supplied id. Rate limiting stays in front. Quota messages must not reveal other users' usage.

## Financial Correctness Considerations
Not applicable to money amounts. Cost control only.

None. The numbers above are the owner's "very low" starting point and are meant to be tuned by changing the constants.

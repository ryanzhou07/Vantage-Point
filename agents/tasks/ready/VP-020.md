# VP-020 — Fix "Mark paid / Mark unpaid" on receivables

## Status
`READY`

## Owner
Receipt Agent (Integration/Review separate)

## Purpose
Owners cannot mark a receivable paid. Every toggle returns `400 INVALID_REQUEST: "Receipt version is required."` The VP-019 receivables endpoint reuses a JSON parser that demands a receipt `version`, but the request body is only `{"paid": true|false}`. Manual paid tracking is the only payment feature in MVP 1 (PROJECT.md "MVP 1 will track payment manually"), so this blocks it.

## Scope
- Backend: make the `version` requirement an explicit option of the shared request parser (`readJSON` in `services/backend/internal/receipts/api.go`) instead of unconditional. `review`, `finalize` and `retry` keep requiring it; `POST /api/v1/receivables/{id}/paid` does not.
- Require `paid` to be present and a JSON boolean on the paid endpoint. A missing `paid` currently decodes to `false` and would silently mark a receivable unpaid.
- Verify `receivable_set_paid` is idempotent: repeating the same transition must return 200 without appending a duplicate `RECEIVABLE_PAID` / `RECEIVABLE_UNPAID` audit event. Fix it with a new migration only if it is not.
- Tests that exercise the real handler path (see Testing).

## Out of Scope
- Payment method (VP-021), Zelle matching (VP-022), search/filter/pagination (VP-023–VP-025).
- Any change to finalization, amounts, or receivable creation.
- Changing the `version` semantics of review/finalize/retry.

## Dependencies
VP-019 merged (it is).

## Requirements
1. `POST /api/v1/receivables/{id}/paid` with `{"paid":true}` or `{"paid":false}` succeeds for the verified owner of an existing receivable.
2. Missing, null, or non-boolean `paid` returns 400 `INVALID_REQUEST`.
3. `review`, `finalize`, `retry` still return 400 when `version` is missing (existing behavior and tests unchanged).
4. Other owners' receivables return the same not-found response as a nonexistent id (no existence leak).
5. Repeating a transition is a no-op for audit history.
6. No parsing behavior is duplicated: one parser, one explicit option.

## Acceptance Criteria
- [ ] Finalize a split, then mark a receivable paid and unpaid through the running app without error.
- [ ] Go handler test posts `{"paid":true}` to a real (fake-store-backed) receivable and expects 200 with `status:"PAID"` and `paid_at` set.
- [ ] Go test: body `{}` and `{"paid":"yes"}` and `{"paid":null}` return 400.
- [ ] Existing review/finalize/retry missing-version tests still pass.
- [ ] Second owner marking the first owner's receivable gets 404.
- [ ] Repeating `paid:true` twice leaves exactly one `RECEIVABLE_PAID` event.

## Testing Requirements
Why this slipped through: the frontend test mocks `receivablesRequest`, and the Go test only hits the invalid-UUID path (returns before parsing). New tests must cross the real boundary.
- Go: handler tests above, including two-user isolation.
- `scripts/test-receipt-integration.py`: add finalize → mark paid → mark unpaid round trip against the local stack.
- Frontend: component test asserts the request body is exactly `{ paid: true }` (no version) and the row updates.
- Targeted run only: `go test ./internal/receipts`, receipts vitest files.

# VP-023 — Receivables search API: filters, keyset pagination, indexes

## Status
`READY`

## Owner
Receipt Agent (Integration/Review separate)

## Purpose
`receivables_list` returns up to 500 rows with no cursor, no filters and a join to two other tables per call. The owner needs to find receivables by date, person and merchant without loading everything. This task makes the query bounded, indexed and filterable. The UI is VP-025; location is VP-024.

## Scope
- `GET /api/v1/receivables` accepts: `status` (`OWED|PAID`, default all), `from` / `to` (receipt date), `q` (participant name or merchant), `limit`, `cursor`.
- Keyset pagination, newest first, with OWED rows before PAID as today. No OFFSET.
- Response: `receivables`, `next_cursor` (empty when finished), `outstanding_minor` for the filtered set. No total-row count.
- Single-table indexed search: snapshot `participant_name`, `merchant_name` and `receipt_date` onto `receivables`. Finalized receivables are immutable (VP-019), so a snapshot cannot go stale. Backfill existing rows in the migration.
- Minimal "Load more" in the existing `ReceivablesPanel` so the default first page never hides rows. Full filter UI is VP-025.

## Out of Scope
Location (VP-024), filter UI (VP-025), payment method (VP-021), full-text/ranking, export, caching of private data.

## Dependencies
VP-019 merged. Reuse the cursor encoding and validation pattern already used by the receipts summary list (`list_test.go` shows `limit` + `next_cursor`).

## Requirements
1. `limit` default 25, max 50; values outside are clamped or rejected consistently with the receipts summary list.
2. Cursor is opaque, owner-bound and tamper-safe; a cursor from another owner or filter set is rejected with 400.
3. `from`/`to` are `YYYY-MM-DD`, `from <= to`, span at most 5 years; rows without a receipt date are excluded when a date filter is present.
4. `q` is 2–64 characters, trimmed. LIKE wildcards (`%`, `_`, `\`) are escaped so user input is literal. Length 2 uses a case-insensitive prefix match backed by a btree `lower(...) text_pattern_ops` index. Length 3+ uses a case-insensitive contains match backed by `pg_trgm` GIN indexes.
5. Unknown query parameters return 400.
6. `outstanding_minor` is a bigint SQL aggregate over the filtered set, not a sum of the current page.
7. Owner scoping comes only from the verified context; queries are parameterized (RPC arguments), never string-built.
8. Rate limiting stays; add a request context timeout (about 5 s). Response sets `Cache-Control: private, no-store`.
9. New migration only: add columns, backfill, create indexes, replace the RPC. Do not edit `20261029000400`.

Indexes (confirm names/types in review):
- `receivables (owner_id, status, created_at desc, id)` replaces `receivables_owner`.
- `receivables (owner_id, receipt_date)` for date ranges.
- GIN `gin_trgm_ops` on `participant_name` and `merchant_name`; btree `lower(...) text_pattern_ops` for 2-character prefixes.

## Acceptance Criteria
- [ ] With 50,000 seeded receivables for one owner, every filter combination returns the first page using index scans only: `EXPLAIN` shows no sequential scan on `receivables` (SQL assertion in `supabase/tests/`).
- [ ] Paging through a seeded set with `limit=2` visits every row exactly once, with no duplicates or gaps, including while a row is marked paid between pages.
- [ ] `q=%` and `q=_a` match literally, not as wildcards.
- [ ] Another owner's cursor or ids never return data (two-user test).
- [ ] `outstanding_minor` equals the sum of matching OWED rows exactly.
- [ ] Existing receivables UI still shows every row via "Load more".

## Implementation Notes
Implemented in migration `20261029000600`: snapshot columns (`participant_name`, `merchant_name`, `receipt_date`) with backfill, `receivables_filtered` + `receivables_search` (keyset cursor, limit clamped to 50, escaped `ILIKE`, filtered `outstanding_minor`), `GET /api/v1/receivables` validation (`receivableQuery`), "Load more" in the panel.
Deviations, with evidence:
- Sort is `created_at desc, id desc` only. Sorting by status first moved a row to the PAID section when it was marked paid between pages and produced a duplicate (found by the 20,000-row paging test). Owed-first is now the status filter.
- No `pg_trgm` or prefix indexes: with the owner btree, the planner chose the owner index even at 20,000 rows for one owner, and one owner's volume is small. Documented as a `shortcut:` in the migration.
- `receivables_list` is dropped (its join became ambiguous once `receivables` gained `merchant_name`).
- Cross-owner cursors are not rejected: the owner filter always applies, so a forged cursor can only reposition within the caller's own rows.
Verified in a scratch database (schema dump, migrations committed, tests run): SQL tests 021-028 pass.

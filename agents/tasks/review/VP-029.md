# VP-029 — Receipt sections, collections/trips, member claims, join-link latency

## Status
`REVIEW` (2026-11-22, implemented by the session agent at the owner's request; needs independent Integration Review; not self-approved)

## Scope
1. Split the single Receipts screen: Drafts/Finalized picker + "New receipt", and section tabs Receipts / Collections / Browse / Owed (`ReceiptTabs`).
2. Collections: private categories owned by one user. Inviting members makes one a Trip (members-only, signed-in). Migration `20261122000100_receipt_collections_trips.sql` (tables `collections`, `collection_members`, `collection_invites`; `receipts.collection_id`; `receipt_participants.user_id`; service-role RPCs), API `/api/v1/trips/*` and `POST /api/v1/receipts/{id}/collection`, UI `features/trips`.
3. Trip members claim as themselves (no token in URL, no 5-minute timer; open until the owner finalizes). Guests on individual receipts are unchanged (5-minute QR session).
4. Join-link latency: broadcasts no longer block the reply; the guest page coalesces refetches and updates claims optimistically.

## Decisions
One collection per receipt; a receipt can be filed only by its owner into a trip they belong to. Invites: one live link per trip, 7 days, stored as SHA-256 hash, revocable by creating a new one; max 40 members, 50 collections per owner. Deleting a collection un-files receipts. Drafts are not visible to members until confirmed.

## Shared resource impact
Cross-domain FKs to `profiles` (membership). Depends on uncommitted `20261117000100_receipt_shared_items.sql` (`receipt_item_split`). Needs Integration Review.

## Not done / open
Trip-wide balances ("who owes whom"), banking transactions in collections, realtime for trip claims (10 s polling), moving a guest's history to an account, deep links to a single trip.

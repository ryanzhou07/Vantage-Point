## Requirements
1. Upload a supported bounded image to private Supabase Storage; database stores its reference. Enforce authentication, owner authorization, actual content/format validation, byte/dimension limits and upload quotas. Do not expose private images through public buckets or cross-user signed URLs.
2. Create durable receipt/job state, queue bounded vision work in the approved worker architecture, and expose processing/error/retry states. Provider requests have deadlines, bounded retries/concurrency and deduplication. Ordinary polling must not enqueue another paid extraction. No new microservice or queue infrastructure without approval.
3. Keep provider structures behind an adapter. Extract merchant/date, item names/quantities/line amounts, subtotal, tax, tip, detectable discounts and total into validated proposals. Treat image text/model output as untrusted data, not instructions or executable content.
4. Vision output is advisory. Owner can add/remove/correct items and correct amounts before a verified split. Surface reconciliation differences; never silently fabricate balancing amounts or ignore discounts. Unsupported receipt cases must show an actionable review state and must not produce a misleading verified result.
5. Owner adds bounded participant names without creating application user accounts. Assign each entire item line to exactly one participant in this first slice. Unassigned lines block a complete split. Split quantities/shared items/custom percentages are explicitly deferred, not approximated.
6. Backend calculates authoritative item subtotals, tax shares, tip shares and totals in exact integer minor units with explicit currency. Offer the approved proportional and equal methods and show the selected methods. Define included participants and reject/resolve undefined zero-weight cases explicitly.
7. Allocate every residual cent deterministically; the sum of participant totals equals the verified receipt total. Use transactional validation and optimistic version/conflict protection so stale edits cannot overwrite newer verified data or create over-allocation.
8. Save and reload the owner-reviewed draft and calculated split preview. Clearly label this a draft/preview. Do not mark FINALIZED, create receivables, imply participant confirmation or collect payment. Full collaborative finalization/revisions/receivables remain later work under the approved design.
9. Reuse UI components with readable route composition. Provide upload progress, processing, review, participant assignment, split summary and error/retry states on desktop and narrow screens. API mutations enforce ownership independent of the UI.
10. Receipt-owned migrations, storage policies, API contracts and worker start/run instructions are required. Keep all provider credentials server-side and out of logs and bundles.

## Requirements
1. Follow PROJECT.md §§4–5, 36, 38, 41 and DESIGN.md §§7–10, 13, 25–28, 31–33, 38–39, 47, 50–51.
2. `auth.users.id` is the canonical user UUID. Profiles reference it and permit one application profile per authenticated user. Do not create a second identity system.
3. Add new migrations for profiles with the designed profile fields, referential integrity, and appropriate least-privilege/RLS rules. Provision profiles idempotently and verify concurrent/repeated access cannot duplicate profiles.
4. Implement Google sign-in through Supabase, callback/session handling, sign-out, and useful loading/error states. Validate redirect destinations and use security protections appropriate to the chosen session mechanism.
5. The Go API validates Supabase sessions/JWTs and establishes identity in request context. Reject invalid, expired, incorrectly issued/audienced tokens; never trust request-supplied user IDs or decode an unverified JWT as authentication.
6. `GET /api/v1/me` returns the authenticated user's application profile only. Document the response and shared request-context contract for consumers. Errors follow DESIGN.md §27; private auth/profile responses must not be shared between users through caching.
7. Bound external validation/key-fetch operations with timeouts and controlled retries/caching as applicable. Document credential/session configuration, CORS, cookie/CSRF decisions, and configurable request protections relevant to the selected mechanism.
8. Keep privileged configuration backend-only. Do not log tokens/authorization headers. Guest receipt participants must not become profiles or canonical users.
9. Use local Supabase and deterministic auth test fixtures in automated tests; actual Google verification is a separate sandbox/manual smoke check, not a production-network CI dependency.
10. Select only implementation details left deferred by DESIGN.md, document material choices, and escalate any change to approved architecture/product semantics.

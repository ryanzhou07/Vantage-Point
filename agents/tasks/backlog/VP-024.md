# VP-024 — Receipt location and location filter for receivables

## Status
`BACKLOG`

## Owner
Receipt Agent (Integration/Review separate)

## Purpose
The owner wants to filter receivables by location. Receipts currently store only `merchant_name` and `receipt_date`; there is no location anywhere (schema, extraction, review editor). This task adds one and extends the VP-023 search to filter on it.

## Scope
- Add `merchant_location` (single text field, max 200 chars) to receipts. Capture it from the receipt image through the existing extraction proposal, and make it editable in the receipt review editor.
- Snapshot it onto `receivables` at finalization (same immutable-snapshot approach as VP-023).
- Add a `location` filter to `GET /api/v1/receivables`, using the same escaping, length rules and index strategy as `q` in VP-023 (trigram GIN plus a lower-case prefix btree).
- Receipts finalized before this task have an empty location and are excluded when the filter is used.

## Out of Scope
GPS or device location at upload, maps or geocoding, structured address fields (city/state/zip), exposing location to participants or on public session views, back-filling old receipts.

## Dependencies
- VP-023 (search API, indexes, snapshot columns).
- Owner decision (below) before READY.

## Requirements
1. Location is optional; an empty value is valid.
2. Extraction adds the field to the provider schema behind the existing adapter; a missing or invalid value falls back to empty rather than failing the receipt.
3. The owner can correct it during review; edits follow the existing versioned save.
4. Location is owner-only data: absent from public session responses and participant views.
5. Filter input is validated, bounded and LIKE-escaped.

## Acceptance Criteria
- [ ] Uploading a receipt with a printed address proposes a location the owner can edit.
- [ ] Finalizing copies the value to the receivable.
- [ ] `GET /api/v1/receivables?location=austin` returns only matching rows, using index scans (`EXPLAIN` assertion).
- [ ] Public session endpoints do not contain the location (test).
- [ ] Old receivables without location still list normally.

## Testing Requirements
Fake vision provider extraction test; versioned save test; SQL migration, snapshot and `EXPLAIN` tests; authorization test that session views omit the field; component test for the editor field. Targeted runs only.

## Shared Resource Impact
Shared contracts: YES (extractor contract `agents/contracts/RECEIPT_DRAFTS` and receivables API). Other domains: NO.

## Database Impact
`NEW MIGRATION` (Receipt): columns on `receipts` and `receivables`, indexes, replaced RPCs.

## Contract Impact
`NON-BREAKING CHANGE`.

## Security Considerations
A shop address combined with dates reveals where the owner spends time. Keep it private to the owner, out of logs, and out of any participant-facing payload.

## Financial Correctness Considerations
Not applicable (no money fields).

## Blockers
Owner decision needed: define "location" as the merchant address or city printed on the receipt, read by the vision provider (recommended: no new permissions, no tracking), versus typed by the owner, versus device GPS (not recommended; privacy and permission cost). This spec assumes the printed-address option.

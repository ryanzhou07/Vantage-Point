# VP-010 — Authenticated Teller connection lifecycle

## Status
`BACKLOG` — depends on the approved VP-009 Teller adapter/mTLS foundation. Owner has clarified this is tied to the existing signed-in Vantage-Point user.

## Proposed owner
Banking Agent, with separate Integration/Review; Foundation consulted only for the existing identity contract.

## Purpose
Allow a signed-in user to enroll an institution through Teller Connect, persist the resulting Teller connection under that canonical user, list it, and disconnect/remove it safely.

## Proposed scope
- Use explicit Sandbox for automated/UI tests, with a separately opted-in Development mode.
- Bind every connection to the authenticated Foundation user on the backend, not a client-supplied user ID.
- Keep Teller access tokens and client certificates server-side; redact them from logs and responses. Persist credentials only through an owner-approved protected/encrypted mechanism; escalate if no approved mechanism exists.
- Provider adapter owns Teller enrollment details. Banking returns normalized Vantage-Point connection state.
- Test two-user isolation, no token leakage, enrollment errors, duplicate/idempotent handling where contracts support it, and disconnect semantics using fakes/Sandbox.

## Dependencies and decisions
- VP-009 COMPLETED.
- Owner approves credential-at-rest mechanism and whether Development with real bank data is in scope for this task or only a later manual smoke.
- Owner confirms removal behavior: revoke/disconnect at Teller and delete local credentials immediately, with minimal audit metadata retained only if approved by DESIGN.

## Out of scope
Normalized financial accounts, balances, transactions, sync workers, webhooks, dashboard aggregation, and profile/settings ownership. No separate microservice or new identity model.

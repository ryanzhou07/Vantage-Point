# VP-022 — Zelle repayment matching from a connected bank (DRAFT)

## Status
`BACKLOG`

## Owner
To be assigned. Not Banking alone: AGENTS.md §9 says Banking does not own "automated reimbursement reconciliation".

## Purpose
When a Zelle participant pays the owner, the owner's connected bank shows an incoming credit. Match it to the receivable and mark it paid, so Zelle rows do not need manual tracking. Venmo stays manual because Venmo exposes no data.

## Scope (draft; finalize when VP-018 lands)
- Consume normalized incoming-credit transactions from Banking through a read-only contract. Receipt code never sees Plaid structures (AGENTS.md §19).
- Match candidates against `OWED` receivables with `payment_method = ZELLE` for the same owner.
- Exact-amount match inside a time window after finalization, plus a payer-name similarity signal.
- Exactly one confident match: mark paid with audit event `RECEIVABLE_PAID_AUTO` recording the transaction id.
- Zero or several candidates: do nothing automatically; surface a "possible match, confirm?" suggestion to the owner.
- Owner can undo an automatic match.

## Out of Scope
- Venmo anything. Moving money. Collecting payee handles. Rewards/forecasting.

## Dependencies
- VP-018 (Plaid banking, accounts and transactions sync) COMPLETED.
- VP-021 (payment method on receivables).
- Owner decision: PROJECT.md lists "automatic reimbursement matching" and automated payment reconciliation as outside MVP 1 (§ out-of-scope, and the manual-payment section). The project owner must amend PROJECT.md (AGENTS.md §25) before this is READY.
- Ownership decision, ideally an ADR in `agents/decisions/`: recommended split is Receipt owns receivable state transitions; Banking exposes a read-only incoming-credits contract.

## Requirements (draft)
1. Idempotent by bank transaction id: one transaction can mark at most one receivable, and replays do nothing.
2. Never auto-mark on ambiguity; suggest instead.
3. Matching is owner-scoped; one owner's transactions never touch another owner's receivables.
4. Pending-to-posted transaction changes must not double-apply.
5. All amounts are integer minor units.

## Acceptance Criteria (draft)
- [ ] Replaying the same transaction does not change state twice.
- [ ] Two receivables with the same amount produce a suggestion, not an automatic mark.
- [ ] Undo restores `OWED` and records an audit event.
- [ ] Cross-owner isolation test passes.

## Testing Requirements
Fake bank provider only; idempotency, concurrency, authorization and financial-correctness tests.

## Security Considerations
Bank transaction data is highly sensitive: no raw transaction payloads in logs or in Receipt tables beyond an opaque id, amount and date.

## Financial Correctness Considerations
Idempotency, duplicate events, and pending/posted reconciliation are the core risks.
